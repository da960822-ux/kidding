# 작업지시 처리 지연 단축 조사와 실행 순서

2026-09-04. 사용자 요청에 따라 AI 계측, BE 실행 경로, 공식 API/실시간 기능을 병렬 조사했다. 아래 성능 설정은 비교 실험이며 아직 제품 기본값으로 적용하지 않았다. 기존 화면·영상·수량·사전 수정과 구분한다. P0 범위는 양파·딸기와 베트남어·네팔어이며, 근로자 TTS 수정은 기존 제외 범위를 유지한다.

## 결론과 측정 경계

큰 병목은 모델 구조화와 번역의 반복 호출·순차 대기다. 구조화의 추론 강도 축소는 이번 표본에서 큰 효과가 있었다. 전체 언어를 한 요청으로 묶는 것만으로는 번역 완료 시간이 충분히 줄지 않았다. 고정 문구 재사용, 독립 필드의 병렬 처리, 중간 크기 번역 묶음과 번역 모델 분리를 함께 비교해야 한다.

직접 Node runtime에 상세 한국어 텍스트를 넣은 측정이다. 음성 인식, 녹음 업로드, Python/DB/인증, Node 프로세스 시작, 실제 TTS와 게시 시간을 포함하지 않는다. guides/assets는 측정 전에 읽었다. 따라서 DB 최적화나 실시간 전사 도입으로 아래 25초가 그대로 줄어든다고 계산하지 않는다.

| 실험 | 구조화 | 양언어 텍스트 package | 관찰 |
|---|---:|---:|---|
| 최초 상세 지시 | 13.253초 | 11.725초 | 합계 24.978초, 6단계, 20망 유지 |
| 호출별 계측 재실행 | 15.540초 | 9.646초 | 합계 25.186초, 7단계; Responses 47회 중 번역 46회, 최대 동시 요청 14 |
| 같은 구조화 요청에서 reasoning low | 4.473초 | 미실행 | 기본 설정 대비 구조화 71.2% 감소, 5단계로 묶였지만 조건·방법·금지·수량 보존 |
| 원래 6단계의 언어별 묶음 번역 + reasoning none | 미실행 | 11.359초 | 기존 11.725초 대비 3.1% 차이. 번역 호출 40→2, vi 4.254초/ne 11.270초 |

각 비교는 한 번의 표본이다. 단계 수가 달라진 재실행끼리 번역 속도 향상을 직접 비교하지 않는다. 낮은 추론 구조화와 묶음 번역을 결합한 전체 경로를 측정하지 않았으므로 두 시간을 더해 새 전체 응답시간이라고 주장하지 않는다. 묶음 번역은 none을 동시에 변경했으므로 각각의 기여를 분리할 수 없다.

구조화 기본 실행은 출력 1,430토큰 중 추론 838토큰이었다. low 실행은 출력 524토큰/추론 0이었으며 원문·prompt·schema를 유지했다. 기본 실행의 입력 3,207토큰 중 3,204토큰은 이미 캐시 HIT였고 low는 캐시 HIT가 없었다. 단순히 캐시가 따뜻해져서 빨라진 결과는 아니다. 반면 번역 46회 중 45회는 이미 추론 토큰이 0이므로 번역의 원인을 추론 강도만으로 설명하면 안 된다.

## 현재 기다리는 경로

1. 농장주 녹음 종료 후 업로드·전사가 끝나야 구조화한다.
2. 구조화 JSON 전체와 검증이 끝나면 농장주에게 초안을 표시한다.
3. 농장주 확정 후 DB 용어/영상 목록을 읽고 양언어 package를 만든다.
4. package는 언어끼리와 단계끼리는 병렬이다. 그러나 각 언어 안의 `장소·마감·메모 → 단위 → 단계`, 각 단계의 `제목 → 설명 → 자막`은 순차적이다. 서로의 결과를 필요로 하지 않는 대기가 포함돼 있다.
5. 같은 선별 동작이 여러 단계이면 같은 제목·자막을 다시 번역한다. 고정 자막도 매번 모델을 호출한다.
6. 현행 게시 경로는 TTS와 양언어 package 검증·DB 게시까지 기다린다. 실험에서는 TTS만 대체했으므로 실사용 확정 대기는 더 길 수 있다.

## 우선순위별 방법

각 항목은 주담당 하나만 둔다. 효과가 실측되지 않은 항목은 가설로 취급한다.

| 우선 | 방법 | 주담당 | 기대 효과와 제약 |
|---|---|---|---|
| 1 | 구조화 전용 낮은 추론 설정 | AI | 한 표본에서 15.54→4.47초. 두 작물·긴 지시·부정·수량·모호성 평가 후 서버 설정으로 적용한다. 모든 작업에 none을 일괄 적용하지 않는다. |
| 2 | 고정 제목·단위·검수 영상 자막 사전 번역 | AI | 현장에서 매번 호출할 이유가 없는 문구를 재사용한다. 기존 DB 용어가 있으면 우선 활용한다. 새 번역은 검수 전 공식 번역으로 표시하지 않는다. 자유로운 상세 설명은 그대로 번역한다. |
| 3 | 같은 요청 안의 동일 번역 중복 제거 | AI | 문자열·언어·segment·작물·사전/문맥이 같은 요청의 Promise를 재사용한다. 저장소 추가 없이 동일 선별 자막 반복 호출부터 제거한다. |
| 4 | 독립 필드의 순차 대기 제거 | AI | context/단위/단계와 제목/설명/자막을 독립적으로 준비한다. 호출 수를 늘리지 않고 의존성 없는 대기를 제거하되 실제 RPM/TPM에 맞게 동시 실행을 제한한다. |
| 5 | 언어별 중간 크기 묶음 비교 | AI | 두 거대 요청만으로 충분히 빨라지지 않았다. context와 단계 묶음 등을 분리해 네팔어의 긴 단일 응답 대기를 줄일 수 있는지 비교한다. field ID·누락·중복·순서를 검증한다. |
| 6 | 번역 모델만 분리 | AI | 구조화는 유지하고 일반 번역을 경량 후보와 비교한다. 특히 네팔어와 농업 단위 품질을 별도 채점한다. 모델 이름만 보고 속도·품질을 보장하지 않는다. |
| 7 | 검증된 번역 결과 캐시 | AI | 동일 자유문구의 반복 요청에도 재사용할 수 있다. key는 원문·언어·segment·작물·prompt/model·사전/참고자료 버전을 포함한다. 검수 철회·변경 시 무효화가 필요하다. |
| 8 | 수량 변경 시 불변 번역 재사용 | AI | 새 version을 만들되 바뀌지 않은 단계/문구의 번역을 재생성하지 않는다. 기존 목표량이 들어간 설명·메모와 관련 출력은 반드시 새로 검증한다. TTS 재사용은 별도 제외 항목이다. |
| 9 | 모델 출력·prompt 포장 절감 | AI | 내부 번역 응답은 ID/text 위주로 받고 version·순서·수량 숫자·URL·출처는 코드에서 결합한다. 작업 방법·조건·예외를 요약 삭제해서 속도를 얻지 않는다. |
| 10 | 요청 단계별 서버 계측 | BE | upload/STT/구조화/catalog/번역/검증/게시/응답 시간을 분리한다. 실제 HTTP p50/p95와 콜드·웜·동시 요청을 측정한다. 본문·쿠키·원음·secret은 로그에 넣지 않는다. |
| 11 | catalog 병렬 조회·기존 FK 조인 | BE | 현재 영상 1회+사전 2회, 총 3번 순차 DB 대기. 기존 helper 병렬로 2번의 대기 단계, 검증된 관계 조회로 2query/1대기 단계를 후보로 둔다. 안전/출처 필터를 유지한다. |
| 12 | 인증 중복 읽기·게시 후 재조회 축소 | BE | 요청 내 검증된 team row 재사용, session/version/link 관계 조회를 검증한다. 새 확정의 non-TTS DB 9회/수량 확정 10회를 줄일 후보다. 권한 결정은 요청 간 캐시하지 않는다. |
| 13 | 동시 동일 확정의 중복 생성 방지 | BE | DB 원자 게시는 이미 보호되지만 두 요청이 RPC 전에 AI를 각각 실행할 수 있다. farm/draft revision/결정 또는 session/version/수량별 single-flight를 검토한다. 전역 잠금은 금지한다. 영속 claim은 별도 데이터 계약이다. |
| 14 | 결정적 실패 재시도 제거·timeout 정렬 | BE | schema/config 오류까지 다시 AI를 호출하지 않는다. 로컬 PostgREST 기본 timeout 120초와 FE 60초의 차이를 명시적으로 관리한다. timeout은 rollback이 아니며 결과 불명 복구를 유지한다. |
| 15 | schema validator 캐시 | BE | 로컬 3.579→1.369ms/회. 매 payload 검증은 유지한다. 작은 비용 절감이며 25초의 핵심 해결책은 아니다. |
| 16 | Node bridge 프로세스 재사용 | BE | 로컬 새 process 중앙값 206.51ms, 이미 뜬 process의 이후 요청 0.55ms. 현재 JSONL loop는 순차 실행하므로 무작정 하나로 공유하면 다른 사용자가 막힌다. 실제 배포 비용 확인 후 수명·취소·routing을 설계한다. |
| 17 | 화면 데이터 분리·불변 package 조건부 조회 | FE | 텍스트를 영상 조회와 분리하고 상태를 즉시 보여준다. 기존 독립 로딩·polling 겹침 방지를 유지한다. 버전/ETag만 확인하는 API는 새 계약이 필요하다. |
| 18 | 농장주가 초안 확인하는 동안 번역 준비 | BE | 확정 버튼 이후의 체감 대기를 검토 시간과 겹친다. draft revision/hash와 사전·자산 버전이 같을 때만 사용하고 보완 시 폐기한다. 불필요한 생성 비용·저장·실패 계약을 먼저 정의한다. |
| 19 | 진행 상태/SSE·검증된 텍스트 먼저 표시 | FE | 최초 표시 시간을 줄인다. 현 adapter/bridge/API 모두 완성 JSON을 기다리므로 stream 옵션 하나로 해결되지 않는다. 미확정·부분 JSON을 근로자 게시 작업으로 보내지 않는다. |
| 20 | 녹음 중 실시간 전사 | BE | 업로드·STT 시간을 발화 시간과 겹친다. 현재 텍스트 25초와 별개의 이득이다. 최종 turn commit, 전사 보완·신뢰도 검증, 임시 credential과 transport 계약이 필요하다. |
| 21 | 실시간 통역 별도 경로 | BE | 발화 중 번역 오디오/자막을 제공하는 대화용 후보다. 구조화·농장주 확정·안전 gate를 대체하지 않는다. ko→vi/ne 현장 품질과 가용성 검증이 필요하다. |
| 22 | 서비스 tier·항상 켜진 서버·지역 배치 | BE | queue/cold-start/네트워크가 실측 병목일 때만 비용과 비교한다. repo의 free/Singapore 설정이 실제 배포 상태를 증명하지 않는다. 모델 fast mode도 계정 가용성과 실제 응답 tier를 측정한다. |
| 제외 | TTS cache-first·비동기 합성·실시간 음성 | BE | 추가 대기를 줄일 후보이나 요청된 근로자 TTS 제외 범위에 속한다. 25초 표본에는 포함되지 않는다. 현재 게시 계약과 별도 설계/검증 대상으로 남긴다. |

## 실시간 번역과 현재 제품의 차이

실시간 전사/통역은 말하는 도중 조금씩 보여 주므로 최초 반응이 빠르다. 현재 제품은 전체 지시의 수량·작업·조건을 구조화하고 농장주 확인 후 두 언어의 검증된 package를 함께 게시한다. 빠른 초안 표시와 검증된 최종 게시를 별도 상태로 다루는 것이 적합하다. 현행 P0에서는 한 언어만 준비됐다고 게시하거나 미검증 내용을 단계 지시로 자동 실행하지 않는다.

GPT-Realtime-Translate는 streaming 통역을 제공하지만 Structured Outputs/function calling을 지원하지 않는다. 확인한 공식 문서에는 ko→vi/ne의 현장 품질 보장이 없어 대체 가능하다고 단정하지 않는다. 일반 `/audio/translations`의 영어 출력이나 24시간 비동기 Batch API도 현장 양언어 즉시 응답의 대체 경로가 아니다.

## 적용·평가 순서

1. 구조화 low만 변경한 후보부터 같은 두 작물 평가 세트로 여러 번 측정한다. 단순 숫자·복합 수량·상세 조건·금지·지원 외 작업·안전 차단이 기존 기준을 통과해야 한다.
2. 기존 번역을 기준으로 중복 제거, 독립 필드 병렬, 중간 묶음, 경량 번역 모델을 각각 비교한다. 하나씩 바꿔 효과를 분리한다. locale별 최종 완료시간과 요청 수·비용·실패율을 같이 기록한다.
3. 빠른 두 단계를 결합해 실제 HTTP 전체 경로를 측정한다. STT/TTS 포함 여부, 사용자 녹음 시간 제외 여부를 명확히 한다. 서로 다른 실험의 빠른 숫자를 더해 제품 속도라고 보고하지 않는다.
4. DB/bridge 작은 개선은 확인된 지연과 구현 복잡도에 맞춰 적용한다. 기존 Origin/cookie/24시간 만료·최신 version·명시적 확인·안전 출처 검증은 제거하지 않는다.
5. 스트리밍, 초안 중 사전 준비, 실시간 전사/통역은 PRODUCT_SPEC→ARCHITECTURE→AI/API/DATA/FAILURE 계약을 먼저 정리한다. 그 전에 무단 partial publish나 임시 DTO를 추가하지 않는다.
